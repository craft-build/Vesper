# 05 — Sending: Messages, Replies, Threads, Reactions

## Goal

Two-way chat: the existing composer sends real messages (with local echo),
reply-to works, thread replies work, emoji reactions toggle — all reflected
instantly in the open timeline and confirmed by the server.

## Deliverable / how to test

1. Send a message in a real room → appears immediately (local echo), loses
   its "sending" state when the server confirms; visible from Element on
   another device.
2. Reply to a message → renders with the reply context line in both Vesper
   and Element.
3. Open a thread, reply → appears in Vesper's thread panel and under the
   thread root in Element (m.thread relation).
4. React with an emoji from `EMOJI_CHOICES` → shows on the message; react
   from another device → Vesper updates live; re-click toggles off (redact).
5. Kill network, send → message stays "queued", sends automatically on
   reconnect (send queue), no loss.

## Context

- Trait methods: `send_message`, `send_thread_reply`, `react`.
- Consumers: `chat/composer.rs` (send, reply state), `chat/message_row.rs`
  (EMOJI_CHOICES, react picker), `chat/conversation.rs` (thread panel).
- SDK: `Timeline::send(...)` takes `RoomMessageEventContent`
  (`.with_relation(...)` for replies/threads); reactions are
  `Annotation`-relation events via `room.send(...)`; the **send queue**
  (`client.send_queue()`) gives offline-queuing + local echoes for free —
  enable it.

## Design decisions

- **Send queue on**: `client.send_queue().enable()` after login. Local echoes
  flow through the same timeline diff stream, so checkpoint 04's pipeline
  shows pending state if the `Message` model gained the pending flag there
  (add it now if it didn't: `send_state: Sending | Sent | Failed`).
- **`react` semantics change**: the trait currently returns `Vec<Reaction>`
  (whole aggregate). Keep the signature; implementation sends a reaction or
  redacts the user's existing reaction of that emoji (toggle), then returns
  the current aggregate from the timeline item — callers get correctness
  without protocol knowledge.
- **Replies**: SDK builds proper fallback bodies via `RoomMessageEventContent`
  relation helpers; strip-by-receiver handled homeserver-side for encrypted
  rooms later. For threads use the thread relation on the root event id.
- **Markdown**: enable the `markdown` feature send path
  (`RoomMessageEventContent::text_markdown`) so existing composer markdown
  keeps working; plain-text fallback auto-generated by the SDK.
- **Errors**: send failures mark the echo `Failed` with a retry affordance
  (retry = `timeline.retry_send`-family API or resend via queue; discard =
  cancel). Keep UI text generic.
- Local echo dedup: SDK already replaces the echo with the remote echo —
  rely on it, don't hand-merge (add a test comment so it isn't "fixed"
  later).

## Implementation steps

1. Enable send queue post-login; log queue status transitions at `debug`.
2. Commands: `SendMessage { room_id, body, reply_to, respond }`,
   `SendThread { room_id, root_id, body, respond }`,
   `ToggleReaction { room_id, event_id, emoji, respond }`.
3. Extend `map_item` to carry `send_state` from `EventSendState`.
4. Composer: Enter sends; show pending/failed styling on rows; reply context
   banner already exists — wire its id through.
5. MessageRow: react picker calls trait method; optimistic UI is handled by
   local echo, so no manual patching of the reactions vec.
6. Failure UX: click failed message → Retry / Discard popup (minimal).
7. Update `MockClient`'s `react`/send paths if signatures changed.

## Acceptance criteria

- [ ] Send → local echo instant → confirmed; survives app focus changes.
- [ ] Reply and thread relations render correctly in Vesper AND other clients.
- [ ] Reaction toggle works both directions with live updates from peers.
- [ ] Offline send queues and flushes on reconnect without duplicates
      (verify event appears exactly once).
- [ ] Failed sends show state and can be retried/discarded.
- [ ] Mock mode still round-trips sends/reactions.
