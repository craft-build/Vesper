## Goal

Vesper becomes a first-class encrypted client: encrypted room history
decrypts (no more placeholders from checkpoint 04), cross-signing is
bootstrapped so the client can be verified, the existing `VerifyDialog`
(SAS/emoji) and device-management UIs work against the real crypto stack.

## Deliverable / how to test

1. Open an encrypted DM that previously showed 🔒 placeholders → messages
   now render as normal text/images.
2. Log into the same account from Element and complete emoji verification
   against this Vesper session using Vesper's VerifyDialog (7 emojis match →
   confirm on both ends → green shield/verified state in both apps).
3. Settings device list shows this device + others with verification status;
   unverified devices are visually flagged.
4. Old encrypted messages sent while Vesper was offline decrypt after
   relaunch (key backup / gossip, if the account has SSSS set up; document
   what works).
5. Message sent from Element into the encrypted DM appears decrypted in
   Vesper live.

## Design decisions

- **Cross-signing bootstrap**: after login/restore, call
  `encryption().bootstrap_cross_signing_if_needed(None)`. If the account
  requires interactive auth (UIAA), surface a targeted error for now —
  password-based UIAA is a stretch goal at the end of this checkpoint.
- **Recovery/key backup**: call `encryption().backups().` … ensure backup
  download is attempted on startup (`wait_for_recovery_sync` / ensure
  `recovery()` is enabled) so historical keys arrive. Keep this behind one
  clearly-named function so it's easy to debug.
- **Devices**: `devices()` = `encryption().get_user_devices(own user)` →
  `model::Device` (id, display name, verified flag, last-seen if available).
- **SAS verify flow** (both user- and device-targeted):
  1. `verify_device`/`verify_user` → fetch verification object,
     `request_verification()` returning `SasVerification`;
  2. accept → poll `.emoji()` → map 7 `Emoji` (symbol, description) into the
     existing `SAS`/`VerifyDialog` props;
  3. user confirms → `.confirm()`, mismatch → `.mismatch()`;
  4. dialog stays open with a waiting spinner until the other side accepts
     (subscribe to `SasVerification` changes stream).
  The trait's narrow `verify_device(device_id) -> Result<()>` doesn't fit an
  interactive flow — extend the trait with a small verification-session
  object API (e.g. `start_verification(target) -> VerificationHandle` with
  `emojis()/confirm()/cancel()`) and keep the old methods as wrappers/or
  remove once UI migrated. MockClient implements the new API with its fake
  happy-path.
- **UTD UX**: keep the placeholder text but append reason classes in `debug`
  logs (historic keys missing vs. withheld vs. sender unverified) to aid
  support; do not expose crypto jargon in UI.
- **Trust shields**: per-room encryption state is available
  (`room.encryption_state()`); adding per-message shields is decorative —
  defer, note it.

## Implementation steps

1. Pass a crypto-store passphrase through session setup (derive/store as
   per design note above).
2. Post-login task: bootstrap cross-signing + start recovery/backup pull +
   `encryption().wait_for_e2ee_initialization` where applicable; all behind
   `tracing` spans so startup hangs are diagnosable.
3. Rework `devices()`; add verification-session API to the trait +
   MockClient fake + `MatrixClient` impl bridging `SasVerification` streams
   to signals (emoji list signal, state signal: `Requested/Ready/EmojisShown/
   Confirmed/Cancelled`).
4. Wire `VerifyDialog` to the new API (it currently takes static emoji data —
   swap for signals; preserve its visual design).
5. Devices tab: show verification status badges; "Verify" button launches the
   dialog with a session for that device.
6. Manual UTD sweep: join an old encrypted room, confirm historical
   decrypt-after-recovery behavior; document results in this doc.
